## v3.4 - Stop and closing release the module: ExpressLRS broadcasts again for any app

**Stop and closing the app now release the module**: ExpressLRS gets `joystick_end`, stops streaming to this PC and broadcasts again, so any app can find it: this app on another PC, [StickTime Pi](https://github.com/juricabi/sticktime-pi), the Linux app, a phone. No more power-cycling the module.

### What was happening

An ExpressLRS module streams to the app that started it until it gets `joystick_end`, loses power or loses its WiFi, and it broadcasts its beacon only while it is not streaming. 3.3 sent `joystick_end` only to restart the stream with a new rate or channel count, so closing the app only stopped *reading*: the module kept streaming to the PC, sent no beacon, and no other app could find it until you switched its WiFi off and on or power-cycled it.

### The fix

- **Stop and closing release the module.** `action=joystick_end` alone goes to the module streaming to the app, then to every module that streams to this PC while the app drops its frames (a frame of it came less than 3 s ago): a second module (the app follows one), a module sending placeholder frames (no stick data), and the module left by Connect to another module IP that streams on. Then to every module asked to start (`joystick_begin`) less than 3 s ago that has not streamed to the app since (it may be about to). Each module gets it once, the ones known to stream first. A module of unknown kind gets it too: an ExpressLRS module streaming since before the app started has sent no beacon. With a module IP set, the app hears no other module's beacons, so one of unknown kind that it neither asked to start nor followed since its Start is left alone: it could be a Crossfire.
- **When**: the Stop button, `s` and `stop` in the CLI, closing the window, *Exit* in the tray menu, and a Windows logoff, restart or shutdown while the app runs (in the tray too). In the CLI also `q`, `quit`, `exit`, Ctrl+C and closing its console window. A logoff or shutdown may end the CLI without a release: quit it first.
- **Closing waits for the answer at most 1.5 s** after the Stop that sent it: closing 1 s after a Stop waits at most 0.5 s more. The `joystick_end` goes out off the UI thread, after anything still on its way to that module, and a quick Start does not cancel it.
- **A release changes nothing else**, except that once the module took it, the app forgets what it asked that module: the module is idle then, and its next `joystick_begin` gives it the rate and channel count, so Stop, another rate, then Connect does not restart it. Its kind stays known. A module that missed its `joystick_end` streams on, as before, and the next session restarts it if the rate or channel count changed meanwhile.
- **Connect** to another module IP still sends the module left nothing at once (no release, no restart); Stop releases it if it still streams to this PC.
- The Stop button and *Exit* in the tray menu say so in their tooltips, and Help has a new section, "Stop and closing release the module".

### The log

| Line | When |
|------|------|
| `Releasing <ip>: joystick_end, so it stops streaming and broadcasts again` | sent |
| `Released <ip>: it broadcasts again, any app can connect to it` | the module answered |
| `Releasing <ip> failed: <why> - it may stream on until its WiFi or power is cycled` | no 2xx answer |
| `Not releasing <ip>: Crossfire broadcasts while streaming, other apps find it as it is` | a Crossfire module |

`<why>` is `HTTP <status>` for an answer that is not 2xx, else the error, such as `timed out after 5 s`; `no answer in time` when closing cut it short, and `not sent, the wait ran out before its turn` for one still waiting behind another request to that module.

### The Linux app and StickTime Pi

This is rule R14 of the protocol rules the apps share, the same in every app: the [Linux app](https://github.com/juricabi/ELRS-Crossfire-WiFi-Joystick-Linux) (v1.1) and StickTime Pi (its exit and its **Release module** button) release the same modules in the same order, with the same log lines, the same Crossfire rule and the same 1.5 s.

### Upgrading from 3.3

- The app saves no settings, so there is nothing to carry over: replace the exe and run it.
- The firewall rule (`ELRS WiFi Joystick`, UDP 11000) still covers the app: no new UAC prompt.
- A module left streaming by 3.3 still streams: Connect to its IP (that moves its stream to this PC), then Stop releases it. Or switch its WiFi off and on once.

### 🛑 Crossfire users

A module known as Crossfire by its `VELOCIDRONE` beacon is **never sent `joystick_end`**: it broadcasts also while streaming, so other apps find it anyway, and what `joystick_end` does to it is unknown. The log says `Not releasing <ip>: ...`. Until its first beacon arrives (about every 8 s), the app can't tell it from ExpressLRS, and a Stop then sends it `joystick_end` like any module of unknown kind.

Broken TBS firmware still breaks the WiFi joystick completely (the module streams, but no stick data arrives, in any client): XF 6.42 and 6.48, WiFi module v3.20. XF 6.31 and 6.36 with WiFi module v2.17 to v3.10 work. See [Crossfire firmware compatibility](https://github.com/juricabi/ELRS-Crossfire-WiFi-Joystick-Windows#-crossfire-firmware-compatibility-important) in the README.

### Requirements
- Windows 7 SP1 to Windows 11 (64-bit), no .NET install needed (self-contained)
- vJoy driver: 2.1.9.1 ([SourceForge](http://vjoystick.sourceforge.net/)) or 2.2.x ([BrunnerInnovation](https://github.com/BrunnerInnovation/vJoy/releases)), with 8 buttons for CH9-CH16
- ELRS TX module 3.4.0 or later (the first with the WiFi joystick), or TBS Crossfire/Tracer

**415 automated tests** (engine, the request and its restarts, the release on Stop and exit, axis and button mapping, both command lines, UI state, vJoy DLL lookup), run by GitHub Actions on every push.
